# Landscape editing rail validation - v0.2.6

## Changes

- **Editing rail.** When the window is wider than tall, the editing tray becomes
  a 104dp two-column rail on the right edge: the six tools in one column; font
  ("Aa" in the current typeface), colour, undo/redo and Done in the other. It
  scrolls if the window is very short. The document area narrows by the rail's
  width for the whole editing session, including while typing hides the rail,
  so the page isn't covered and doesn't reflow mid-edit. No bottom height is
  reserved for the tray in landscape. Portrait is unchanged.
- **Overlays.** The curved scrollbar, zoom label and notices shift left of the
  rail; the selection bar and save button already sit inside the document area.
- **Document options.** In landscape, the preview sits on the left and a
  320–440dp panel slides in from the right, instead of a bottom sheet that left
  the preview only a sliver of height.
- **Home** recents cap at 640dp and centre. The **signature canvas** is shorter
  in landscape (strokes are normalised by width, so signatures are unchanged).

## Evidence

- ktlint passes. 191 JVM tests pass.
- 74 instrumented tests pass on a fresh install (API 35 emulator), including the
  new `DocumentEditingTrayTest`: the vertical rail has its fixed width, tools
  stack in one column beside the action column, and tool selection and Done
  work.
- The instrumented suite runs in portrait. The landscape reader layout, the
  side-by-side document options and the Home width cap were **not** checked
  live: the emulator could not be opened for interactive viewing in this
  session, so no landscape screenshots or hand checks were made.
