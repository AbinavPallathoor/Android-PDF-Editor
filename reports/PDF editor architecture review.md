# Restore reliable PDF editing across pages

**Rebuild the document session and reader/editor surfaces selectively; do not rewrite the whole app or replace every PDF library.** The clarified requirement is adding annotations and visual signatures across all pages, which the existing native Compose and PDFBox foundation can support. The app currently presents one fixed bitmap page for writing, but its exporter appends real PDF text/vector content: source inspection does **not** show a screenshot-only PDF export. The central defect is fragmented page-local editing state and incomplete open/save/share integration. Keep PDFBox as the first writer candidate, prove editable annotation round-tripping, and evaluate a modern PDFium binding only if portable text extraction or rendering fails a focused spike. Preserve minSdk 26, compileSdk 36, AGP 8.13, offline operation, and the approved license policy.

## One durable session must own every page and save

Introduce one document session containing source URI/access capabilities, private base and working revisions, ordered **stable page IDs**, PDF-space annotations/history per page, saved/dirty revision identity, view preferences and a recoverable manifest/journal. Index is navigation state; reordering changes ID-to-index mapping rather than moving annotations onto unrelated content. Both layouts and editing observe this session. One crop/rotation/zoom/translation transform must serve rendering, overlays, selection and export.

Serialize mutations and render lifecycle. Current structural edits can mutate a file still held by the renderer, and concurrent edit coroutines have no session operation lock. Close renderer access before writing, create a fresh private revision, validate reopening, then promote it and invalidate render/text/thumbnail caches together. Save and share must snapshot **all pages and the latest structural revision**, with unique immutable share files. ([structural lifecycle](</Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:180>), [editor](</Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/data/pdf/PdfBoxEditor.kt:16>))

The corner icon represents unsaved document changes; undo back to the saved state clears it. **Save as new file remains the default**; choosing Save to current file is explicit overwrite opt-in. A complete output PDF is normal even for one changed annotation: incremental writing is a separate optimization, and PDFBox warns against using its source as incremental output. ([PDDocument](https://raw.githubusercontent.com/TomRoush/PdfBox-Android/master/library/src/main/java/com/tom_roush/pdfbox/pdmodel/PDDocument.java))

Current-file saving requires actual write grants/provider support; Open with can supply temporary read-only access. Persist only offered grant modes and add Recents only after persistent read is confirmed. Generate and validate a full temporary export before touching the destination, preserve recovery data, handle null/failed streams, close successfully and verify reopening. Provider writes are not universally atomic, and `w` need not truncate. Retain dirty state on cancellation/failure and clear only the revision actually saved; newer edits stay dirty. Persist pending export identity across recreation. ([SAF guidance](https://developer.android.com/training/data-storage/shared/documents-files), [ContentResolver semantics](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/content/ContentResolver.java#1541))

## Prove persistence before polishing gestures

**Phase 1 — opening and feasibility:** verify cold/warm/repeated VIEW routing, revoked/read-only/writable grants, persistence and Recents. Spike standard annotation round-trip and PDFBox text selection on rotated/cropped/mixed-size PDFs, ligatures, CJK and RTL. Compare PDFium only against documented failures; inspect exact resolved artifacts and licenses.

**Phase 2 — session and saving:** annotate/sign multiple pages, change modes, reorder/delete/append, save once and reopen every page. Confirm saved objects remain editable, repeated saves do not duplicate marks, share includes pending edits, save-copy preserves source bytes, and only explicit current-file saving changes the original. Exercise cancellation, provider failures, storage exhaustion, process death, edits during save and recovery.

**Phase 3 — reader interactions:** verify both layouts, normalized reading position, normal-color default/persisted inversion, long-press copying, fit-page zoom, pan bounds and discoverable Pages access. Inject gradual multi-pointer gestures through Compose touch tests, then exercise them on a device; adb swipe alone cannot validate this classifier. Check annotation alignment on all four rotations and offset CropBoxes in both preview and reopened exports. Finish with large-document memory/rendering checks and release APK/license/no-INTERNET validation.

**Evidence boundary:** the coordinator reports `assembleDebug` succeeded and a fresh forced JVM run passed **23 tests, zero failures/errors/skips**. No adb device was attached. No interaction, annotation round-trip, provider overwrite or export comparison was tested this turn; overview evidence is source inspection plus model simulation. Only research artifacts changed, and existing working-tree changes were preserved.

## Conclusion

The first implementation gate is a reliable, recoverable document session and a proven annotation/text backend. That separates necessary architectural repair from an optional renderer replacement, while giving the requested save menu and multipage editing a consistent source of truth. A successful build cannot establish this gate: reopened exports, saved annotation editability and real provider/gesture behavior must decide readiness.
