# PDF document lifecycle, opening, and saving audit

## Why does Open with open the app but not the chosen PDF?

### Takeaway
This is a confirmed source integration omission, not evidence that the PDF renderer needs replacement. The manifest advertises PDF viewing, but neither the cold-start intent nor warm-start intent reaches document navigation.

### Cited Findings
- The manifest declares `ACTION_VIEW`, `application/pdf`, and `singleTop`, but `MainActivity.onCreate` only builds the usual navigation tree. It does not inspect `intent.action`/`intent.data`, and there is no `onNewIntent` override. The graph always starts at `HomeRoute`; only picker/recents callbacks navigate to a reader. Sources: [manifest](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/AndroidManifest.xml:12), [MainActivity](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/MainActivity.kt:35), [NavGraph](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/nav/NavGraph.kt:47).
- Android delivers a new intent to an existing top `singleTop` activity through `onNewIntent`. Its `getIntent()` still returns the old intent unless `setIntent()` updates it. Sources: [task lifecycle](https://developer.android.com/guide/components/activities/tasks-and-back-stack), [Activity API](https://developer.android.com/reference/android/app/Activity#onNewIntent(android.content.Intent)).
- The picker attempts to persist both read and write grants, catches `SecurityException`, then invokes the open callback anyway. Despite its comment claiming otherwise, the callback unconditionally records the document in Recents, and neither HomeViewModel nor RoomRecentsRepository checks persisted permissions. Sources: [picker](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/MainActivity.kt:16), [navigation callback](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/nav/NavGraph.kt:54), [repository](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/data/db/RoomRecentsRepository.kt:16).
- Persistability requires a grant offered with the persistable flag; temporary external VIEW grants are not automatically permanent. Android's SAF guide demonstrates masking returned flags to the granted read/write modes. Sources: [ContentResolver implementation and API comments](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/content/ContentResolver.java#2942), [SAF guide](https://developer.android.com/training/data-storage/shared/documents-files).
- `ACTION_SEND` is not declared as an incoming action; the manifest comment mentioning a share sheet overstates the implemented intent filter. Source: [manifest](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/AndroidManifest.xml:23).

### Inferences
- Use one `OpenDocumentRequest` path for picker, cold VIEW, warm VIEW and recents. Parse and validate the incoming URI and MIME, retain actual grant capabilities, and queue navigation until the graph is ready. Consume requests once to avoid reopening on recomposition/restoration.
- Track session access separately from durable reopenability. Permit temporary read-only documents to open, but add Recents only after persistent read is confirmed, or clearly mark/recover ephemeral entries. Capture raw activity-result flags with a custom result contract if needed; do not request persistence for a write mode the provider did not offer.
- Receiving another document while edits exist should preserve the current durable session rather than silently discard it.

### Gaps
- All app findings above are source-confirmed only. No emulator/device reproduction was performed by this researcher. Coordinator reported no attached adb devices.

## What is actually edited, exported, retained, or lost?

### Takeaway
The app adds real PDF vector/text operators when exporting; it does not export a screenshot. However, the interactive editor is intentionally a single raster page with an in-memory overlay, and the save/share/session wiring never collects annotations from the whole document.

### Cited Findings
- Writing is explicitly one page at fixed fit-width with no pan/zoom. ReaderScreen captures `writingPageIndex` on entry, supplies empty initial annotations, and saves only the active page's list. Sources: [WritingScreen](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/writing/WritingScreen.kt:89), [ReaderScreen](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderScreen.kt:152).
- Each writing VM uses `writing-$pageIndex`; it holds annotations/history in memory. Saved reusable signatures are persisted separately, but document annotations are not. The reader back-stack entry's VM store can retain those per-page VMs across mode toggles: switching modes alone is not proof of annotation loss. Reading does not draw these overlays, and the export callback cannot access the other page VMs. Sources: [VM construction](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/writing/WritingScreen.kt:108), [WritingViewModel](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/writing/WritingViewModel.kt:17), [mode branches](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderScreen.kt:153).
- Save copies the full current working PDF (or original) to a dedicated export file and calls `flattenAnnotations(source, mapOf(pageIndex to annotations))`. The flattener loads the PDF, appends page content streams, writes stroke/signature path operators and text operators, then saves the full PDF. Thus an export contains every existing PDF page, but only the current page's pending annotations. Sources: [save callback](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/nav/NavGraph.kt:152), [flattener](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/data/pdf/PdfBoxAnnotationFlattener.kt:23).
- Flattening is permanent page content, not editable standard PDF annotation objects; the code does not recover those operators into its own model when reopening. Source: [flattener](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/data/pdf/PdfBoxAnnotationFlattener.kt:15).
- Save always launches `CreateDocument`. There is no replace-original action, dirty revision, saving state, success acknowledgement, or reset-to-saved baseline. Pending export is merely `remember { File? }`; the result copies via a nullable output stream without a visible error path. Activity/process recreation while the picker is open can lose this association. Sources: [launcher](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/nav/NavGraph.kt:92), [save](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/nav/NavGraph.kt:152).
- Share uses `currentWorkingFile` or the original URI, never the writing annotation state or generated annotated export. A user can save annotations and then share the untouched original; when structural edits exist, sharing includes those edits but omits pending writing overlays. Sources: [share](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/nav/NavGraph.kt:133), [working-file ownership](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:72).
- Structural operations mutate a private working file and reload the renderer. Its path is held only in `workingFile`; a recreated VM starts from the original URI, not an existing working copy. No document-session manifest or recovery exists in these paths. Sources: [initial open](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:91), [structural edits](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:180), [copy/reload](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:217).
- Subsequent structural edits can write the same working PDF still held by PdfRenderer: the old engine closes only after opening a new renderer following mutation. Independent edit coroutines have no session mutex/operation queue. Editor methods save over their input path rather than promote a validated new revision. Sources: [ReaderViewModel](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:180), [reload close order](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:237), [PdfBoxEditor](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/data/pdf/PdfBoxEditor.kt:16).
- Null input streams are treated as a successful copy in `ensureWorkingFile`, and append/export have similar nullable-stream paths. Source: [copy helper](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:218), [append/export](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/nav/NavGraph.kt:94).
- Invert resets to `true` at initial open; toggle only updates transient UI state. Room has no invert/view-mode preference fields. Sources: [initial state](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:111), [toggle](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderViewModel.kt:174), [entity](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/data/db/RecentDocumentEntity.kt:11).

### Inferences
- Page-index ownership is unsafe: after reorder/delete the same `writing-0` VM can refer to different page content. Introduce stable session page IDs and an ID-to-current-index mapping. Collect all pages' annotations in the document session, not composable-owned per-page VMs.
- A replaceable session/editing architecture is needed regardless of renderer choice. Replacing PDF libraries alone fixes none of the confirmed intent, save, share, preference or recovery omissions.
- A save icon should reflect a document revision differing from its committed revision, including structural edits. Undo back to the saved state should clear it. Both save targets and share should use the same immutable snapshot/export pipeline.

### Gaps
- No actual PDF output was generated or inspected in this research task. Runtime corruption, PDF fidelity across arbitrary documents, and process-recreation behavior remain unverified. Source code establishes risky lifecycle order, not a claim that every edit corrupts files.

## Recommended architecture, remaining reader causes, and acceptance checks

### Takeaway
Keep the existing domain boundaries and offline constraints, but replace fragmented page-local edit/save ownership with one durable, serialized document session. The clarified requested scope is annotations/signatures on all pages, not rewriting existing PDF paragraph content.

### Cited Findings
- SAF `ACTION_CREATE_DOCUMENT` creates a new file and cannot overwrite an existing one. Replace-original should instead target the already-authorized original URI. For document providers, query `FLAG_SUPPORTS_WRITE` directly; `DocumentFile.canWrite` can also be true just because deletion is supported. Source: [SAF guide](https://developer.android.com/training/data-storage/shared/documents-files).
- Output mode `w` is provider-defined and might not truncate; supported modes include `wt`/`rwt`, with provider-dependent semantics. Streams can return null after provider failure and can throw file/IO errors. Source: [Android ContentResolver source](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/content/ContentResolver.java#1541).
- Private files shared through FileProvider need temporary read grants; the current manifest/provider/read-flag approach is directionally correct, but the shared payload must come from a complete stable export snapshot. Sources: [Android sharing guide](https://developer.android.com/training/secure-file-sharing/share-file), [share implementation](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/nav/NavGraph.kt:133).
- Coordinator's additional source audit found: long press explicitly opens the scrub overlay; the reader uses a `LazyColumn`, with no paged alternative or text-selection overlay. Zoom minimum is 1x fit-width. Sources: [ReaderScreen](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ReaderScreen.kt:166), [ZoomMath](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/ZoomMath.kt:10).
- The overview classifier checks ratio >1.6 only while unclassified, but locks into PINCH once deviation exceeds 0.15. Coordinator's one-off Python model simulation of gradual 30-frame gestures yielded ratio 1.811/PINCH when growing and 0.545/PINCH when shrinking; only a single jump to 1.7 classified OVERVIEW. This is source audit plus model simulation, not an Android gesture runtime test. Source: [classification](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/reader/PinchZoomGesture.kt:106).
- Writing renders to full viewport bitmap bounds, while PdfPageTransform maps both axes using width alone. Unless viewport and PDF aspect ratios match, preview y coordinates and saved PDF y coordinates differ. Sources: [bitmap](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/writing/WritingScreen.kt:203), [transform](/Volumes/FortKnox/01_Projects/AppDev/Pdf_Editor/app/src/main/java/com/pdfeditor/app/ui/writing/PdfPageTransform.kt:17).

### Inferences
- Proposed session: source URI/access capabilities; private base/working revision; stable ordered page IDs; per-page PDF-space annotation models and history; dirty/saved revision IDs; durable journal/manifest; view preferences; operation mutex. Reader and writer observe the same session; page navigation and display modes change presentation only.
- Preserve actual page aspect ratio and use one tested transform covering crop box, rotation, zoom and translation for render/overlay/text selection/export. Do not stretch the PDF to the viewport.
- Persist normal/inverted PDF preference and view mode separately from app chrome. Default new documents to normal PDF colors per user request, retaining the black application background unless separately changed.
- After any edit, show the requested corner save icon. Tap opens a small menu with **Save to current file** and **Save as new file**. New-file action remains default. Enable current-file action only with actual write access and provider support; for read-only VIEW grants offer SAF authorization or save-copy instead of falsely promising replacement. User choosing current-file is the explicit overwrite opt-in.
- Serialize render shutdown/edit/snapshot/reopen. Write private revisions to fresh files, validate they reopen, then atomically promote within app-private storage. Never overwrite the file currently backing a renderer or a share recipient.
- Before replace-original, finish and validate the entire local export, preserve recoverable original/private data, and then attempt an explicit truncating provider write with surfaced failure. Do not promise atomic replacement across arbitrary SAF providers. Retain the draft on failed/cancelled writes and report success only after successful stream close/reopen verification. Clear dirty only for the exact revision saved; edits made during save remain dirty.
- Persist pending export identity across recreation. Share should take a unique immutable snapshot with all annotations/structure applied, so a recipient never sees a file concurrently rewritten by subsequent edits.
- Acceptance checks: cold VIEW, warm VIEW from another open document, repeated same URI, missing/revoked grants, read-only and writable providers; no launcher navigation regressions. Multi-page annotate/sign then change modes/pages, reorder/delete/append, save once, reopen and verify every page. Verify source bytes unchanged for save-copy and changed only for explicit replace. Cancel/fail save, provider null/IO failure, process death with picker open, process death mid-draft, undo to saved state, repeated saves without duplicate ink, edits during saving, and share before/after save. Verify aspect/rotation/crop-box placement visually and by reopened export. Test actual gradual multi-touch overview entry, text copying, fit-page zoom and both display modes on emulator/device. No product tests were added or run by this researcher.

### Gaps
- Coordinator baseline verification: `assembleDebug` succeeded (48 tasks up to date); forced `:app:cleanTestDebugUnitTest :app:testDebugUnitTest` succeeded, with XML reporting 23 tests, zero failures/errors/skips. These establish build/JVM baseline only, not runtime validation of this report's proposed fixes. No attached adb device was available.
- Provider-specific atomicity, removable-volume failures and physical-device behavior need runtime tests. Library choice for selectable text and standards-based annotation persistence belongs to the parallel library feasibility review; this audit does not claim a particular replacement SDK is necessary.
